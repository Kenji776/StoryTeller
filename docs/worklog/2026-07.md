## 2026-07-27 — Round-based turns, feasibility gate, newbie advisor

**Goal:** Make play properly round-based (initiative roll, order, 3-minute turns),

**Changed:**
- `lobbyCombat.js` — `rollInitiative` (d20 + DEX mod, shared comparator); `startGame`

  round number; a returning player keeps the seat they already rolled.
- `lobby/turnAttempts.js` — 3-strike tracking on the persisted lobby.

**Decisions:** One capability model with two consumers, so the advisor can never

## 2026-07-27 — Pluggable TTS with a local speech server

**Goal:** Let narration run through a self-hosted TTS server instead of
ElevenLabs, with the host choosing the engine and voice per lobby.

**Changed:**
- `services/tts/` — new provider layer: `registry.js` (the only list of engines
  plus selection policy), `narrate.js` (frames → Socket.IO, engine-agnostic),
  `wavTiming.js`, and adapters for the local server and ElevenLabs.
- `routes/ttsService.js` — reduced to HTTP translation; gained
  `/api/tts/providers` and a `provider` parameter on the voice routes.
- `lobby/lobbySettings.js` — `ttsProvider`, and a per-provider voice memory so
  switching engines does not lose the voice chosen for the other one.
- `server.js` — boot probe, `resolveTTS`, `ttsActiveFor`, `LOCAL_TTS_URL`.
- `client/tts.js` — buffered Blob playback beside the MediaSource path.
- `client/components/options.html` — engine dropdown; voices reload per engine.

**Decisions:** [ADR 0005](../decisions/0005-pluggable-tts-with-a-local-server.md).
The local server's URL is an env var, not a lobby setting — the server issues that
request, so a host-editable field would be an SSRF vector. Word timings are
approximated from the WAV duration rather than dropping the highlight feature.
Declined transcoding to MP3 (needs ffmpeg; project has no native deps) and Web
Audio streaming (disproportionate for an engine running 11× realtime).

**Verification:**
- `npm test` → 815 pass, 0 fail (was 609). RED observed before each unit per `TDD-2`.
- `npm run test:integration` → 7 pass against the real server on 127.0.0.1:8199;
  re-run with an unreachable URL → 7 skipped, 0 failed.
- Live boot: both engines detected; `/api/tts/providers` reports both; voices list
  from each; local preview returns 139 KB of `audio/wav`; unknown voice → 500.

**Open:**
- **The browser half is unverified.** No DOM harness exists and adding one means a
  dependency this project has avoided, so `client/tts.js` buffered playback and the
  new options dropdown are syntax-checked and reviewed only, never run in a browser.
  This is the first thing to exercise by hand.
- Player lines fall back to the DM's voice on any non-ElevenLabs engine, because a
  character sheet's `voice_id` is an ElevenLabs id. Mapping characters onto local
  voices is not done.
- Local audio is uncompressed WAV: ~48 KB per second of speech over the socket.
  Fine on loopback or LAN, not over a WAN.
- Buffered synthesis means first-audio latency scales with narration length —
  roughly 12 s of silence for a 2000-character narration.
- `keyfile.age` sits untracked **and unignored** in the repo root (`GIT-5`).
  Pre-existing, not introduced here, but one `git add -A` from being committed.

## 2026-07-27 — Combat had no stakes; the enemies' turn is now the server's job

**Goal:** three full games produced no `player:death`. Find out why and fix it.

**Evidence:** across two games the DM emitted an `hp` block on 4 of 92 turns and a
negative delta on 2, while constant fighting produced 117 XP events. Damage was not
being dropped — it was never generated. Strengthening the prompt moved it from 0
damaging turns in 57 to 2 in 92, which is not stakes. Nothing was wrong with the
plumbing; the narrator simply will not do combat arithmetic mid-scene.

**Changed:**
- `server/services/enemyTurns.js` — new. Rolls every living enemy's attack against
  the target's AC, spreading attacks round-robin rather than focusing one character.
  Attack bonus and damage scale with challenge rating. Both dice are injected so
  tests are exact (`TDD-8`).
- `server/server.js` — resolves the enemies' round *before* the DM writes and hands

## 2026-07-27 — The host's credential: consent, limits, expiry, and who pays

**Goal:** second phase of the credential work — the per-lobby store for a host's
supplied key and the single path that decides whose key serves a call. Pure
modules again, wired to nothing, so the tree stays collision-free with the other
agent working in `server.js`.

**Changed:**
- `server/services/credentials/sessionKeys.js` + test — host keys in memory,
  consent required, call limits, expiry, six purge paths, spend ledger.
- `server/services/credentials/resolve.js` + test — host key → shared key →
  local service → typed refusal. `CredentialRequiredError` with `userMessage()`.
- `docs/decisions/0014-…`, `docs/modules/credentials.md`, `docs/architecture.md`
  (the invariant paragraph described a store that did not exist yet), README.

**Decisions:** ADR 0014. Three worth repeating here.

Consent is a required argument to `put`, not a checkbox the server trusts the
browser to have rendered — a host funds every player's turns and there was no
record anyone had told them so.

The secret and the spend ledger have different lifetimes on purpose. ADR 0003
drops the credential on *every* host disconnect and re-sends on rejoin, so a
ledger sharing that lifetime would reset on each network blip and a 200-call
limit would mean 200 per reconnect. `dropSecrets` clears one, `forget` clears
both. This asymmetry is the thing most likely to be "tidied" away later; it is
commented at the point of definition and pinned by a test.

An expired or exhausted host key throws rather than falling back to the
operator's. Falling back would move the bill to someone who never agreed to pay
it, at the moment they are least likely to notice — the same reasoning ADR 0003
used to reject migrating the host role.

## 2026-07-27 — Image generation becomes a provider layer

**Goal:** operator now runs a self-hosted image server on the LAN and wants it
available. Portraits were a single function in `llmService.js` holding an OpenAI
client built at module load, so there was nowhere to put a second generator.

**Changed:**

**Decisions:** ADR 0015.

The parameters the image server documents as "leave alone" have no code path
rather than a correct default. `cfg` is the one that matters — the model is
distilled for the server's value and raising it produces burnt output, silently,
with no error. A value in a request body is one somebody later makes
configurable; having no path is a stronger guarantee. Three tests assert `cfg`,

fixed by trying another model; a 403 *is* how that API reports a model this
organisation may not call, which is exactly what the ladder exists for. The
distinction is on `status`, because `classifyHttpStatus` folds 401 and 403 into
one `auth` kind.

Sizes are mapped rather than refused — the local server takes any multiple of 16,
OpenAI takes three fixed strings per family, and a caller asking for a portrait
shape should get a portrait from either.

## 2026-07-28 — Playing on the hardest setting, and why it was unwinnable

## 2026-07-28 — Initiative on death and removal

**Goal:** the operator asked whether initiative is updated correctly, in logic and UI,
when a player or enemy leaves combat.

**Mostly yes, with one real defect.**

Enemies are not in the initiative order at all — it is players only, and they take
their actions through the share-out. So an enemy dying cannot desynchronise it.

All five removal paths (`gameUpdates` on death, admin kill, disconnect, inactivity
kick, and the timer) call `removeFromTurnOrder` and emit `turn:update` carrying the
fresh order. `client/components/initiative.html` listens to both `turn:update` and
`state:update`, so it re-renders on either. The enemy list it draws comes from
`state:update`, which the action handler emits on the success *and* the parse-failure
path — so an enemy killed on a turn whose narration failed to parse still disappears.

**The defect:** removing the last player in the order wrapped `turnIndex` to 0 without
advancing the round. A wrap *is* a round, and swallowing it stalls the counter —
which, since the `actedInRound` work earlier today, means enemies never get their
action back. Traced:

```
order=[A,B,C] turnIndex=2 round=1   C is up
C dies      → order=[A,B] turnIndex=0 round=1   ← round should be 2
nextTurn    → turnIndex=1 roundAdvanced=false
```

`nextTurn` cannot catch it afterwards: by then the index is at the top and the wrap
looks like an ordinary step.

**Changed:** `server/services/lobby/lobbyCombat.js` — that branch now advances the
round. `docs/modules/combat.md` gained an initiative section, and its description of
the share-out was corrected, having still described the positional model replaced
earlier today.

**Verification:** `npm test` → 2297 passed, 0 failed (up 5). RED observed 1/77, with
the four neighbouring cases (mid-order removal, current-turn removal, emptying the
order, removing a non-member) green throughout, so the fix is confined to the wrap.

**Open:** unchanged — the timer path still resolves the whole roster because it does
not know the round.

## 2026-07-29 — Draft portraits no longer decide a character's face

**Goal:** the operator noted players re-generate their portrait several times while
building a character, and only the version brought into the game should count for
continuity.

**It was worse than "extra records".** Every press of Generate reached
`POST /characters`, so the identity every later scene matched against was minted from
whatever the sheet said at some arbitrary press — and because `characterPlan` mints a
new identity when the appearance changes, editing the sheet between presses retired
one identity and created another. The canonical face was effectively "whichever draft
was last".

**Changed:**
- `ensureCharacterImage` takes `register` (default true). False draws the picture and
  touches no identity, returning any likeness the character already had rather than
  null — a draft must not appear to erase an established face either.
- `registerCharacterLikeness` — new. Stores the likeness and draws nothing, since the
  picture the player sees was already rendered separately. Reuses an unchanged
  identity rather than paying for another reference render.
- `/api/character-image` passes `register: false`.
- `game:start` calls `registerPartyLikenesses`, which fixes every member's face from
  the sheet they actually brought in. Not awaited and never rejecting: a character
  that fails to register loses scene-matching, which is smaller than a game that will
  not start.

**Verification:** `npm test` → 2322 passed, 0 failed. RED observed 4/43.

Live, against a running server:
- a draft portrait rendered in 8.4s and produced **zero** registration log lines
- starting a game produced `🎭 Registered the likeness for Brannor Ironfoot as
  chr_d324e0bd`

**Note on the image server's brief:** it recommends `GET /characters` on startup to
reconcile, and `identity_strength` tuning. Neither is done. The first matters if
records outlive lobbies; the second is the alternative to the free render, kept in
reserve.
